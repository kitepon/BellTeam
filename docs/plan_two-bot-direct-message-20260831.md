# 二体Bot直接メッセージ計画

## 目的

メインサーバーの BellTeam コンテナ内に `bell-grok-a` と `bell-grok-b` を定義し、両者が MCP の `sendmessage(target, message)` だけを使って直接メッセージを一往復できるようにする。

## 成功条件

- Codex CLI と Grok CLI が BellTeam コンテナ内に公式導入経路から入っている。
- 各 Bot が専用プロジェクトフォルダと tmux セッションを持つ。
- 両 Bot から同じ `sendmessage(target, message)` MCP ツールを呼べる。
- ツールが宛先 Bot の定義を引き、tmux セッションが無ければ起動する。
- `bell-grok-a` から `bell-grok-b` へ届き、`bell-grok-b` から `bell-grok-a` へ返信が届く。
- 成立した配送が JSONL に送信元、宛先、時刻とともに残る。

## 実装契約

- Bot 定義は BellTeam が所有する一つの構造化ファイルへ置く。
- MCP の公開ツールは `sendmessage` 一つだけとし、引数は `target` と `message` だけにする。
- 送信元は MCP プロセスの `BELLTEAM_BOT_ID` から決め、呼び出し側へ指定させない。
- tmux の起動、CLI ごとの貼り付け、送信、受理確認はツール内のアダプタが行う。
- セッション名、プロジェクトパス、起動コマンドを Bot の定義から解決する。
- 配送不能を成功へ丸めず、MCP のエラーとして返す。

## 非目標

- 受信箱とメッセージ受信ポーリング
- 管理画面、HTTP API、ユーザー認証
- Peertable の着席と円卓会話
- Claude Code 対応
- Bot の動的作成

## 既知の罠

- tmux pane の shell へ本文を送るとコマンドとして実行される。CLI が前面にいることを確認してから配達する。
- Codex と Grok は TUI の貼り付け・送信挙動が異なる。差は MCP 内のアダプタだけに置く。
- room 保存や tmux コマンド成功は Bot の受理成功と同じ事実ではない。入力欄から本文が消え、CLI が受理した状態を確認してから記録する。
- 認証ファイルの内容をログ、計画、証跡、イメージへ入れない。コンテナ専用の永続領域へ秘密を表示せず移す。

## 工程

1. サーバー環境、CLI、認証、既存Bot資産を読み取りで確認する。
2. MCP、Bot定義、起動処理、CLIアダプタを実装し、偽の tmux で focused test を通す。
3. Docker イメージと Compose を作り、コンテナ内で両 CLI の起動と認証を確認する。
4. 実 Bot 間で一往復し、配送ログと双方のセッション履歴を確認する。
5. 関連試験、差分、証跡を確認し、成果をメインサーバーへ残す。

## F/A/H

- F: MCP 公開契約、認証の扱い、コンテナ構成、実機受入、最終合否。
- A: なし。実装は親が直接行う。
- H: なし。既存の認証がコンテナへ移せない場合だけ、利用者によるログインを必要条件として停止する。

## 並列化

同じ小規模リポジトリの設定、MCP、試験が密結合するため、親が直列に実装する。書込みWorkerは使わない。
