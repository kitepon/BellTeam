# Cursor冷間起動と配送状態の修正

## 目的

停止中のBotへ送ったメッセージを確実にAIへ渡し、BellTeamの表示を実際の配送結果と一致させる。

## 変更範囲

- Aitermは、Cursorへ貼り付けたプロンプトが入力欄へ反映されたことを確認してからEnterを送る。
- Aitermは、Enter後に本文が入力欄から消えたことを確認して送信成立とする。
- BellTeamは、受付時を`queued`、処理中を`running`、完了時を`delivered`、失敗時を`failed`として記録する。
- 失敗したメッセージを成功表示のまま消さない。
- 修正版を本番へ反映し、停止状態の4ハーネスを確認してから、なぎへ落ちた2件を再配送する。
- 全Bot共通のオーナー情報を各CLIのグローバル指示へ生成する。
- Bot固有の名前、人格、役職、役割、前セッションの短期記憶を各Botプロジェクトの`AGENTS.md`へ生成する。Claudeの`CLAUDE.md`は`@AGENTS.md`で参照する。
- 起動時の会話プロンプトと長期記憶・RAGの一括注入を廃止し、最初から実メッセージだけを送る。
- DMとルーム配送の識別IDは内部だけに保持し、AIへは固有名詞を`「」`で示す自然な会話文脈と実本文を渡す。
- ルーム返信先は現在処理中の配送から内部判定し、Botは返信または沈黙だけを返す。
- 保存済みの最終セッションIDへ最初に配送し、不達時だけ起動して返却された最新IDへ更新する。
- ThroughlineへBotのprojectを渡す一回の呼び出しで、会話本文を持つ最新sessionの短期記憶を案内なしで取得する。

## 原因

- Cursorの冷間起動では、画面表示後も入力処理の準備に時間がかかる場合がある。
- Aitermは固定時間後にEnterを送り、貼付内容の反映前に送信操作を行っていた。
- BellTeamはAIの処理完了前にメッセージ記録へ`delivered`を固定で付けていた。

## 非目標

- 常時起動、監視、配送キューの永続化
- 反復再試行、追加ID、新しいセキュリティ対策
- ハーネスごとに異なるBellTeam配送処理

## 既知の罠

- Aiterm一覧の`agent_done=true`は終了監視が有効という意味で、処理完了ではない。
- Cursorは同じプロンプトでも冷間起動時だけ送信が遅れるため、内容の差を原因と誤認しない。
- ユーザーメッセージは画面へ即時表示する必要があり、完了まで記録自体を遅らせない。

## 実装順

1. Cursorの貼付反映前にEnterを送る現行挙動をfocused testで固定する。
2. AitermのCursor送信処理を画面状態ベースへ変更する。
3. BellTeamの配送状態を同一delivery IDの状態イベントとして記録し、表示時に反映する。
4. 両製品の関連試験と全試験を通す。
5. 起動指示、実メッセージ配送、ルーム返信相関、最終セッションIDの契約をBellTeamへ実装する。
6. Aitermを公開し、BellTeamを本番更新する。
7. 停止状態のClaude、Codex、Cursor、Grokで受信と応答を確認する。
8. 失敗した2件をなぎへ再配送し、応答を確認する。

## 受入条件

- Cursorは貼付内容の反映前にEnterを送らない。
- Cursorは入力欄から本文が消えるまで送信成功を返さない。
- BellTeamの表示状態が`queued`、`running`、`delivered`または`failed`へ実結果どおり遷移する。
- 起動失敗を`delivered`として表示しない。
- 4ハーネスの停止状態テストが成功する。
- 起動時にオーナー情報、Bot情報、前セッションの短期記憶をこの順で読める。
- ClaudeのBot固有指示は`CLAUDE.md`から`AGENTS.md`を参照する。
- 長期記憶とRAGは保持したまま、起動時には一括注入されない。
- 新規作成と再起動で偽の挨拶・引き継ぎ会話を生成しない。
- 最新sessionが空でも、その前に会話本文を持つsessionから短期記憶を取得できる。
- DMとルームのAI入力およびWebタイムラインに配送IDを表示しない。
- 記録された最新セッションIDがプロセス再起動後の最初の配送先になる。
- なぎが落ちた2件を受信し、処理を開始する。

## 進め方

Aitermの返却契約をBellTeamが使うため、二つのリポジトリは直列に変更する。書込みの委譲と並列実装は行わない。

## 実測結果（2026-09-03）

- Cursor: Aiterm 0.29.29で貼付反映待ちとCSI-u Enterを実装し、停止状態から受信・返信を確認した。
- Claude: 停止状態で本文だけがcomposerへ残る失敗を再現した。原因は貼付反映待ちではなく、AitermがClaudeのsession IDを起動時に採番するため、dispatch前のTUI起動待ちがClaudeだけ常に省略されていたこと。Aiterm 0.29.30で、完了eventも進行中turnもないClaude sessionを他harnessと同じready gateへ通す9行の修正を入れた。
- BellTeam本番をAiterm 0.29.30へ更新後、Claude・Codex・Grok・Cursorの4体を停止状態から再試験し、全て受信と返信、配送記録`delivered`を確認した。Claude画面では本文がcomposerへ入ってから送信されている。
- 一時Codex試験Bot（bot-cab5b78e）は削除済み。Bot数27。
