# 知らせ1件ごとの全件読み直しと、待機接続の5秒切断

ビルド35で残っている時間切れ（`-1001`、bots・rooms・owner）と通信断（`-1005`）を調べた記録。トロニー、2026-10-03 22:38〜23:00 UTC。

## 測ったこと（本番、読み取りだけ）

- `GET /api/bots` は3,706,696バイト。うち `avatar`（29人分のJPEGのdata URL）が3,603,945バイトで97%。`/api/owner` は約400KB（ほぼアバター）、`/api/rooms` は約149KB（うちアバター約136KB）。`cache-control: no-store`、圧縮なし。
- `/api/events` を120秒読むと `messages` が20件（1時間あたり約600件）。同じ変更で5〜7ミリ秒の間に2〜6件続く塊が4回あった。50msでまとめると11件になる。
- アプリ（`AppStore.startEvents`）は知らせ1件ごとに `refreshFromView()` を待ってから次の知らせを読む。`refresh()` は bots・rooms・owner を並行で取る。1件あたり約4.26MB。会話画面は同じ知らせで messages と queue も読む。
- ベルチームの実機35の記録では、22:30:17〜22:34:22 UTC の4分5秒に完了した通信が588件（すべて200）。
- 応答ヘッダは `Keep-Alive: timeout=5`（Nodeの既定）。

## 判断

- 22:00:12.845/.847/.849 UTC の bots・rooms・owner の時間切れは4ミリ秒以内にそろっている。同時に始めた3つの取得が同じ接続の停止で一緒に切れた形で、`refresh()` の並行取得と合う。停止のきっかけ（背景での中断、回線の変化、接続の死）はこの記録からは決められない。
- 前面にいる間ずっと重い取得が続くため、接続が一度止まるたびに複数の取得が巻き込まれる。発生回数を増やしている要因は、知らせ1件ごとの全件読み直しと、一覧へ埋め込んだアバター。
- `Keep-Alive: timeout=5` は、LANなどでサーバーへ直接つなぐ端末で `-1005` を起こす既知の形（待機5秒の接続を再利用する瞬間にサーバーが閉じる。Apple QA1941）。公開URLの端末はCloudflareとの間の接続が切れるので、これだけでは説明できない。診断に端末と経路が無いため、どちらの端末の記録かは分けられない。

## サーバーの変更

- 一覧に `avatarVersion` を足し、`?avatar=omit` で画像本体を外す。画像は版つきURLで配る（`immutable`、`If-None-Match` で304）。指定の無い取得は変えない。
- `messages` の知らせを50msの間は1件にまとめる。
- 待機接続を125秒保つ。止める時に処理中だった接続は、応答を返し終えたら閉じる（待機時間の満了まで停止を待たせない）。

## 残り（アプリ、ビルド36）

- 知らせ1件ごとの `refresh()` をやめるか間引く。一覧は `?avatar=omit` で読み、アバターは版が変わった時だけ取る。
- 冪等なGETは `-1005` で1回だけ取り直し、取り直しも失敗した時だけ診断へ送る。POSTは再送しない。
- 背景へ移る時に進行中の読み直しを取り消す（ベルチームが再現と修理を実測済み）。
- 通知登録の失敗が `IOS_PUSH_FAILED` と settings の `IOS_NETWORK_FAILURE` へ二重に数えられる。片方にする。
- 診断へ端末種別・経路（公開/LAN）・前面/背景・経過時間を足す。今の記録では原因を端末ごとに分けられない。
