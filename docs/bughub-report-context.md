# 通信診断の集約と調査終了

通信失敗は、要求した操作・期待・観測結果が分かる範囲を記録する。原因や画面の回復を観測していなければ、固定の分類や保持処理の存在から実害・原因・回復を推定しない。

要求traceを持つ既存の診断文脈から、許可した操作と観測結果、サーバー例外の段・型・原因符号で既存fingerprintを算出する。会話GETとPOST、HTTP500と502、接続拒否と接続切断を同じ集約へ入れない。管理一覧の説明にも操作・結果・原因未特定を表示する。原因符号は低水準の観測であり、製品の根因確定とは異なる。

未知・不正・重複した文脈、trace無しの報告は従来の集約へ残す。旧fingerprint・回数・原文を書き換えたり、新しい文脈で過去の欠測を補ったりしない。新しい発生は通常どおり加算し、閉じていても再発として開く。

現存資料で過去の根因を特定できず、追加取得の現実的な手段がない報告は「情報不足・原因特定不能」で調査を閉じる。修理済み・無害・再現しないことを意味しない。閉じる理由と既知の事実/欠測を中央へ残し、発生原文・累計・重大度を保持する。別途特定した製品欠陥は、その修理・実配布・受入を独立に追う。

管理APIのresolve/reopenは、任意の`note`（空白だけを除く2,000文字以内）を状態変更と同じ保存経路へ渡す。`POST /api/admin/logs/annotate`は`{fingerprint, note}`で注記だけを追記/更新し、既存resolvedを再resolveしない。注記は診断原文と別の`investigation_note`へ記録時の累計・状態・時刻と保存する。管理GETでは、既存設置別注記`investigation`のsummary/evidence/updated_atを上限まで無変更で保ち、新noteを`diagnostic_context.investigation_note`へ投影する。中央の既存signature adapterが両方を別々に取り込むため、既存注記を連結・切詰めしない。再発でopenになっても理由を失わず、どの累計までの調査かを表示する。Bearerと既存管理口の契約は共通。

本文・query・認証・任意のエラー本文は新しい文脈へ出さない。原因符号は固定allowlistだけ、未知はunknownとする。報告受付・要求の再送・重大度の契約は変更しない。
