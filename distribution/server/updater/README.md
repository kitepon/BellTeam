# Host update admission and worker source

This component is not installed by copying a socket into the server container. Initial Host installation is a separate privileged change, reviewed by Root with the OS owner. Subsequent accepted updates use the same programmatic path from the application and authorized automation; they do not require a per-update SSH or AI procedure.

## Layout and dependencies

The fixed Host prefix is `/srv/bellteam/shared/tools/bellteam-container-update-host`. All ancestors of executable code, import closure, policy and catalog must be root-managed, non-symlink and not writable by other identities. Existing shared ancestors must not be chmod/chowned to make this pass. If the proposed prefix does not meet the conditions, installation fails and its location must be resolved before enabling the service.

- `releases/<sourceSHA40>`: immutable code closure from one explicitly approved OCI image, directories 0555/files 0444. `root-code-paths.json` is the image-to-Host path contract; distribution generates `root-code-manifest.json` with the final source and all file sizes/SHA256. The pinned receipt and complete inventory are rechecked before each entry.
- `catalog/releases/<SHA64>/{catalog.json,installation.json}`: verified catalog bytes and authentication receipt. `catalog/state.json` is the sole adoption/revocation/clock record. A newer verified release without committed state blocks plans until repair. Same timestamp/different digest and older publication are rejected; revoked digests are never forgotten by later omission.
- `state`: root/0700, files 0600. Request/plan/worker records, fixed locks and non-secret outcomes. Ledger retains 4096 request tombstones and refuses new operations at capacity; active/unknown requests are never silently discarded. Unreferenced expired plans are removed and live plans are capped at 64.
- `installation`: root/0700 private installation configuration, including the frozen normalized `normal.json`. Existing credential references and configuration remain in this private configuration domain, never in the public operation ledger. Its `operations/<planId>` stores installer input and previous configuration. This is separate from user-facing results.
- `socket`: root:1001/0750, `update.sock` root:1001/0660. Keep this parent inode stable across daemon restarts. Only this directory is bind-mounted read-only at `/run/bellteam-updater`; do not mount code, state, catalog or Docker socket into normal.

Canonical root-managed Python >=3.11, Node, Docker plus Compose, `/usr/bin/gh` with the official attestation verification flags, the system manager/systemd-run, and the shell are required. No user NVM, HOME, PYTHONPATH, NODE_OPTIONS, Docker context or inherited application environment selects code. The verifier is launched with isolated Python and only the validated immutable sibling directory explicitly added for its imports. The frontend cannot access Docker; its cached current observation is revalidated by the separate worker before accepted is returned.

## Initial configuration

`config.json` is a root-managed non-secret file at the prefix. Its complete keys are `schema,release,installRoot,projectName,python,node,docker,systemdRun,shell,platform,writePaths`. Schema is `bellteam.host-updater.installation.v1`; release is a full source SHA, platform is `{os:"linux",arch:"amd64"|"arm64"}`, and writePaths is the reviewed fixed data/configuration closure for the worker, not caller input. Tool paths are canonical absolute files. installRoot and its ancestors must protect the saved generations from unprivileged rename.

The root-only `installation/normal.json` must be the approved normalized current model with absolute data/HOME paths and explicit volume names. App-code binds must refer to immutable root-managed source. `--probe`, run in its own privileged service, verifies the actual CID/image/source and actual bind/volume/subpath/RO metadata against that model, then publishes a non-secret current observation. A user-owned existing checkout must not be imported/executed as root; an initial controlled configuration transition may be required. This is part of the Host introduction plan, not a per-update task.

The root-only code publisher `scripts/install-container-update-code.py APPROVED_OCI_REF EXPECTED_SOURCE_SHA` creates an unstarted, network-disabled image container, copies only the fixed inventory, verifies all hashes, publishes once with NOREPLACE and removes the helper container. It does not register/start services or modify the normal container. The immutable OCI digest/source are explicitly approved bootstrap inputs, not values trusted from the image's own claim. The publisher itself must already reside in a verified root-controlled bootstrap location.

Before enabling a service, render only `@PYTHON@` and `@RELEASE@` in the unit templates from the validated installation config, inspect the complete units and verify them on the target systemd version. The admission unit has empty capabilities, AF_UNIX, strict filesystem protection and Docker socket masking. Its fixed write paths are state/socket. The worker uses a distinct transient system service, Type=exec/Restart=no/KillMode=control-group, and the configured reviewed write closure. It has no PartOf/BindsTo relationship with the daemon or normal. `setsid` alone is not the lifetime boundary.

## Catalog supply and operations

Initial catalog acceptance is `container-update-host.py --install-catalog CATALOG BUNDLE ROOT_EXPECTATION`; root expectations have exactly catalogSha256/sourceCommit/signerCommit. Common operation does not accept these paths. `--refresh-catalog` discovers only formal `updates-YYYYMMDDTHHMMSSZ` releases at the fixed GitHub repository and verifies the bytes using the fixed publisher policy before any root adoption. Release metadata only selects a candidate. The supplied timer runs ordinary program code, not an AI monitoring loop. No catalog/expired/revoked/clock uncertainty means no executable plan; a download or CI candidate is not a formal published update.

The Unix protocol is one finite UTF-8 NDJSON request/response (64KiB, five-second connection limit, maximum 16 simultaneous handlers). Operations are capabilities, catalog(componentId), plan, start and get. Plan and request IDs are canonical UUIDv4 from the common API. Plan fixes the verified catalog/target, actual current binding and five-minute deadline. Start requires the restart confirmation and returns accepted only after durable intent and worker receipt/binding. Same ID/same plan is a read; different plan or a different parallel request is rejected. Ambiguous handoff/worker loss stays unknown and is never automatically rerun.

The worker calls the existing installer from immutable root code, supplies a private captured previous model/runtime proof, preserves data paths and uses the existing recover operation on failed installation/verification. It confirms selected image ID, source and healthy runtime, including storage binding, before completed. Cleanup uses the existing cleanup core with the exact previous image and is reported independently: a cleanup failure does not roll back a healthy target. Only fixed codes/non-secret identity are returned to applications.

## Stop, rollback and removal

Stop admission first and inspect active/unknown ledger entries. Restarting admission must not stop its independent worker. Do not treat Host reboot or worker termination as idle; retain unknown and reconcile the same request ID. Updating the helper uses a separate verified release and a pinned unit; retain the old release while any worker references it. A helper rollback must understand the existing ledger and must not restore an old ledger snapshot.

Removal disables new admission, preserves active/unknown workers/results, and removes only the reviewed units/socket leaf/mount. Do not delete the shared prefix's ancestors or other products. Removing/recreating the socket parent requires replacing the normal bind; restarting only the socket leaf does not. Initial Host registration/restart/removal and container changes require Root's concrete introduction decision; none were performed by the source tests.

## Evidence limits

Direct source fixtures exercise real files/flocks, private atomic state, the actual installer subprocess boundary with an artificial installer/engine, an independent worker process and Unix client disconnect. Ownership is substituted with the current UID and signature receipts are stubs. They do not prove production root/1001, systemd cgroup separation, real Docker migration, official crypto, formal publication, Host installation or real delivery. These require the separate disposable native acceptance with fixed source and artifacts. The current coding environment has no systemd-analyze; no unit activation was attempted here.
